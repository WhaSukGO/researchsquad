# R12: 같은 폴더의 파일 교체가 EXDEV로 중단된 문제

2026-10-31. 이번 작업은 파일 게시 경로를 수정하고 실제 OS 조건에서 검증한 것이다. 모델 선택·학습 성능 연구나 경험 저장 기능을 추가한 작업이 아니다. 과거 실패 실행은 변경하지 않았다.

## 어떤 업무가 중단됐는가

기존 `reliability-managed-03`에서 Experiment Engineer는 숫자를 정렬하는 코드를 작성하고 Docker에서 실행했다. 중앙 런타임이 산출물을 보존하려던 중 `ArtifactStore.register()`의 `content.tmp → content` 이름 교체가 `EXDEV`로 실패했다. 업무 W-0001은 WAITING에 남았다. 정렬 알고리즘의 오류도, 모델이 잘못된 도구를 고른 결과도 아니었다.

원래 예외의 두 경로는 같은 부모 폴더 안에 있었다. 따라서 ‘임시 파일을 Linux /tmp에 만들고 Windows D:로 옮겼다’는 설명은 이 실행과 맞지 않았다. 단순 산출물 등록 100건씩을 DrvFS와 ext4에서 반복한 앞선 검사는 모두 통과했으므로 실패 조건을 포함하지 못했다.

## 어떻게 원인을 좁혔는가

먼저 Windows에서 임시 파일과 대상 파일 각각을 열고 공유 옵션을 바꾸는 8가지 조건을 확인했다. 삭제 공유를 허용하지 않은 여섯 조건은 EACCES, 삭제 공유를 허용한 두 조건은 성공이었다. 이 검사에서는 EXDEV를 재현하지 못했다. Windows 읽기 잠금만으로 원인을 설명하지 않았다.

다음으로 WSL 마운트 기록에서 D:에 대한 두 개의 겹친 마운트를 확인했다. 같은 장치와 같은 경로여도 서로 다른 마운트 인스턴스일 수 있다. 기존 코드는 원본과 대상의 절대 경로를 각각 해석했다. 두 해석 사이에 마운트가 바뀌면 원본과 대상이 서로 다른 인스턴스에 속할 수 있다. Linux의 [do_renameat2 구현](https://github.com/torvalds/linux/blob/v6.6/fs/namei.c#L4640-L4652)은 이 경우 EXDEV를 반환한다. 이 설명은 커널 코드에 근거한 가설로 세우고 실제로 시험했다.

재현 도구는 root의 **별도 마운트 namespace** 안에서 새 검사 폴더만 같은 폴더 위로 bind mount했다가 detach했다. init namespace 실행과 공유 마운트 전파는 거부한다. 호스트의 기존 마운트를 바꾸거나 에이전트 컨테이너에 mount 권한을 주지 않았다. Python에서 OSError를 만들어 던지는 방식도 사용하지 않았다.

첫 DrvFS 비교에서 기존 절대 경로 방식은 5,000번 중 7번 EXDEV가 발생했고, 같은 부모 directory descriptor를 사용하는 방식은 5,000번 모두 성공했다. Linux ext4에서도 같은 오류를 재현했다. 따라서 Windows 파일 잠금과 구분되는 **경로 해석 중 마운트 인스턴스가 바뀌는 경쟁 조건**이 같은 폴더 EXDEV의 재현 가능한 원인임을 확인했다.

다만 과거 managed-03의 실패 순간에는 마운트 추적 기록이 없었다. 당시 어떤 프로세스가 마운트를 바꿨는지, 당시 오류가 반드시 이 경로에서 발생했는지는 확정하지 못했다. ‘과거 사건의 촉발 주체까지 규명했다’고 주장하지 않는다.

## 무엇을 바꿨는가

`goalagent/contracts.py`의 공통 파일 게시 함수가 부모 폴더를 한 번 열어 고정한다. 고유 임시 파일의 생성, 쓰기·flush·fsync, 원자적 이름 교체, 실패 시 임시 파일 정리까지 모두 이 descriptor를 기준으로 수행한다. 원본과 대상의 경로를 다시 각각 해석하지 않는다. [Python os.replace](https://docs.python.org/3.12/library/os.html#os.replace)의 src_dir_fd와 dst_dir_fd에 같은 값을 사용한다.

JSON 상태 저장과 산출물 내용 저장이 같은 구현을 사용한다. 산출물은 이전의 고정된 content.tmp 대신 고유 임시 이름을 사용한다. 완성한 내용을 게시한 다음에만 산출물 metadata를 작성한다. JSON 상태는 기존의 0600 권한을 유지한다. 컨테이너가 읽는 비밀정보 없는 control 파일의 명시적 권한 설정도 유지한다.

진짜 EXDEV에 복사·삭제 fallback을 적용하지 않았다. 권한·점유 오류에 대한 기존 제한 재시도는 파일 이름 교체에만 적용한다. 모델 호출이나 shell·학습 명령을 반복하지 않는다. 쓰기·fsync·이름 교체 실패에서는 기존 대상과 산출물 수용 경계를 유지한다.

## 수정 후 검증

최종 수치와 실행별 경로는 같은 폴더의 verification.json에 보존한다. 실제 마운트 경합 비교는 기존 방식과 수정된 production 함수를 각각 실행한다. 오류율은 환경과 타이밍에 좌우되므로 일반적인 장애 확률이나 처리 속도 개선율로 해석하지 않는다.

- 실제 DrvFS 마운트 경합: 기존 방식 5,000번 중 EXDEV 78번. 수정된 JSON 저장 1,000번, 산출물 등록·재읽기 1,000번 모두 통과했다. 이는 초기 비교 이후 production 함수를 검사한 별도 실행이다.
- 실제 ext4 마운트 경합: 기존 방식 20,000번 중 EXDEV 5번. 수정된 JSON 저장 300번, 산출물 등록·재읽기 300번 모두 통과했다.
- 실제 Windows 읽기 잠금: 수정된 저장 함수에서도 EACCES 네 번 뒤 잠금 해제 후 정상 교체를 확인했다. 이 재시도는 파일 교체만 반복했다.
- 경계 회귀: 부모 경로가 바뀌어도 고정한 폴더에 게시하고 정리하는지 확인했다. 쓰기 도중 실패, fsync 실패, EXDEV에서는 임시 파일·부분 산출물·성공 metadata가 남지 않는지 확인했다. JSON EXDEV는 재시도·복사하지 않고 이전 내용을 보존했다.
- 실제 Docker 업무 흐름: 실패한 보호 측정 → 수정 → 독립 역할 검토 → 완료 → 재열기 추가 호출 0을 확인했다. 역할의 결정은 고정 시나리오이며 실제 모델 추론으로 세지 않았다.
- 실제 Docker 학습 작업 운영: 호스트 재열기, 20MB 체크포인트, 시간 제한, 취소가 통과했다. 이 검사는 CPU 운영 검사이며 GPU 학습 정확도를 다시 측정한 것이 아니다.
- 관련 회귀 45개 통과 후 전체 회귀 **162 passed, 3 skipped**. 생략한 항목을 실제 실행한 것으로 세지 않았다. 위 Docker 실행은 별도로 수행했다.

재현 명령은 WSL의 repo 디렉터리에서 다음과 같다. 각 명령에는 새 디렉터리를 사용한다.

```sh
sudo unshare --mount --propagation private /home/ws/.cache/researchsquad/verify-venv/bin/python -m scripts.probe_mount_publication --run-dir tmp/NEW-MOUNT-PROBE
```

Windows 읽기 잠금 검사는 PowerShell에서 `scripts/probe_windows_state_lock.ps1 -RunDirectory <새 절대 경로>`로 실행한다. 이 재현 도구들은 유지관리자 검사이며 에이전트가 실행할 일반 도구 목록에 추가하지 않았다.

## 판단과 남는 한계

재현된 마운트 인스턴스 경합은 경로를 고정하는 수정과 production 함수의 실제 재검사로 대응했다. 단순히 새 실행 한 건이 통과한 것을 수정 근거로 삼지 않았다. 기존 Team 단일 상태 기록, 독립 검토, 보호 평가와 불확실한 명령의 재실행 금지 규칙은 유지했다.

과거 실패 순간의 촉발 주체, 정전 직후의 저장 내구성, 모든 WSL·네트워크 파일시스템 조합을 검증한 것은 아니다. 저장소가 계속 사용 불가능하면 오류를 보고하고 운영자 복구를 기다린다. 이번 검사에는 실제 모델 호출이 없으며 자율 연구 판단이 좋아졌다는 결론은 내리지 않는다.
