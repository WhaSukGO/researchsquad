# 딥러닝 연구 에이전트 평가 프로젝트 기획안

작성일: 2026-10-30. 이 문서는 **실행할 연구와 필요한 시스템 확장의 기획안**이다.
아래 모델을 학습했거나 표에 적힌 성능을 달성했다는 보고서가 아니다.
코드 작성 능력보다 데이터 선택 → 근거 확인 → 가설 → 실제 학습 → 실패 분석 →
통제된 비교 → 재현의 연결을 평가한다.

## 1. 현재 구현과 의도한 시스템 사이의 차이

현재 역할은 같은 Agent에 서로 다른 프롬프트·도구를 주어 실행한다. 엔지니어가
학습 스크립트를 작성하고 허용된 환경에서 실행할 일반적인 통로는 있다. 그러나
유지관리자가 제공하는 GPU 학습 환경, 긴 학습 작업의 수명 관리, 대형 체크포인트,
훈련/검증/테스트 데이터 계약과 모델 평가기는 아직 구현되어 있지 않다.

에이전트의 판단에 쓰는 Codex 모델은 외부 제공자의 추론을 사용한다. 우리가
학습시키려는 CNN·음성 모델·악보 모델은 별도의 로컬 연구 대상이다. CNN의 가중치를
업데이트하는 것과 에이전트 자신의 기반 언어 모델을 학습시키는 것은 구분한다.

### 이 머신에서 직접 확인한 사실

| 항목 | 확인 결과 | 이 결과로 말할 수 있는 범위 |
| --- | --- | --- |
| GPU | NVIDIA GeForce RTX 3080 **Laptop GPU**, 16,384 MiB | 데스크톱 3080 10GB를 가정하지 않는다 |
| CPU / RAM | 논리 CPU 16개 / 물리 RAM 약 63.7 GiB | WSL에 실제 배정된 자원은 별도 확인 필요 |
| 디스크 | D: 여유 공간 약 28.6 GiB | 확인 시점의 여유 공간이며 다운로드·이미지·중간 파일 예산이 필요 |
| WSL | Ubuntu 24.04, WSL2에서 GPU 정보 조회 성공 | GPU가 WSL에 노출됨 |
| Docker | `--gpus all` 컨테이너에서 같은 GPU 조회 성공 | Docker GPU 전달이 작동함 |
| 실제 CUDA 연산 | 드라이버 API로 커널을 실행해 19+23=42 확인 | GPU 연산 경로 확인. PyTorch 학습이나 처리량 측정은 아님 |
| 현재 Agent 설정 | GPU 옵션 없음, 메모리 2GB, CPU 2개 | 기본 에이전트 실행은 GPU를 사용하지 않음 |

실제 커널 검사는 [수동 CUDA 검사 스크립트](../scripts/probe_cuda.py)로 재현할 수 있다.
이 스크립트는 에이전트에게 GPU 권한을 주는 런타임 도구가 아니다.

검사 도중 Ubuntu 재실행이 `HCS/ERROR_SHARING_VIOLATION`으로 실패했다. Windows에서
Docker를 직접 호출하는 대체 경로는 동작했다. 다른 작업의 디스크 잠금을 강제로
해제하거나 WSL 서비스를 재시작하지 않았다. 장기 학습 전에 Ubuntu 실행 상태도
다시 점검해야 한다. 하드웨어 확인 기록은
[hardware-training-readiness-20261030.json](verification/hardware-training-readiness-20261030.json)에 있다.

**GPU 사용률 100%를 시스템 성공 기준으로 삼지 않는다.** 데이터 다운로드, 논문 읽기,
검증과 보고 단계까지 GPU가 바쁠 이유는 없다. 학습 구간에서 샘플/초, GPU 대기 시간,
메모리 최고점, 검증 품질/시간을 측정한다. 무의미한 연산으로 GPU를 채우는 것은
연구 성능이 아니다. PyTorch는 DataLoader 작업자 수, 메모리 전송과 혼합 정밀도를
측정하며 조정하도록 안내한다. [PyTorch 공식 가이드](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html)

## 2. 먼저 필요한 변경 — 아직 구현되지 않음

| 실제로 해야 할 업무 | 현재 막히는 지점 | 필요한 구현과 확인 |
| --- | --- | --- |
| PyTorch 모델을 RTX 3080에서 역전파 | `DockerSandbox.command`가 GPU를 전달하지 않고 `Team.policy`는 2GB/2CPU로 고정 | 호스트가 승인한 CPU/GPU 실행 프로필, CUDA·PyTorch 이미지, 장치/AMP/역전파 준비 검사 |
| 2시간 학습을 유지하고 진행 상황 확인 | `run`은 동기 실행이고 기본 명령 120초·역할 600초 제한 | 시작/상태/종료 도구, 작업 ID, 실행 기록, 체크포인트 기반 재개. 프롬프트로 제한 해제를 대신하지 않음 |
| ResNet·Whisper 체크포인트 전달 | 파일 16,000,000바이트, 묶음 64,000,000바이트 제한 | 별도 모델 저장소와 작은 참조 영수증. 파일 경계를 무조건 크게 늘리지 않음 |
| 공개 학습 데이터 수만 개를 여러 실험에 재사용 | 일반 입력 묶음은 64MB이며 작은 명시적 파일 전달에 맞춰짐 | 읽기 전용 데이터셋 저장소, 버전·분할 목록, 전처리 캐시, 학습 라벨과 비공개 평가 라벨 분리 |
| 학습된 모델을 독립적으로 채점 | 현재 일반 평가기는 텍스트 스냅샷을 받음 | 유지관리자 소유 모델 로더·추론 코드·평가 데이터와 이진 모델 산출물 계약 |
| GPU 메모리 부족 후 유효한 실험으로 복구 | 일반 오류는 기록하지만 GPU 작업 예약·자원 추적이 없음 | 단일 GPU 예약, OOM 원인 기록, 배치 크기 변경을 별도 실험으로 등록, 마지막 정상 가중치 보존 |
| 읽은 논문과 실행한 저장소를 연결 | 검색 도구가 차단될 수 있고 성공한 읽기만으로 실험 수행이 증명되지 않음 | 검색 공급자 설정/대체 입력, 논문 주장→실험 설정 표, 실제 체크아웃 버전과 패치 기록 |

실행 프로필의 초기 제안은 GPU 한 개, CPU 최대 8개, 시스템 RAM 최대 24GiB,
VRAM 목표 상한 12GiB이다. 실제 가용 메모리와 다른 사용 중인 프로그램을 확인한
후 확정한다. 데이터·이미지·가중치 저장 후 D: 10GiB 이상을 남기는 조건으로 시작한다.
이 숫자는 측정된 최적값이 아니며 실행 전 계약의 출발점이다.

모델 평가기는 에이전트가 만든 Python 모듈이나 pickle을 호스트에서 실행하지 않는다.
검증한 구조 설정과 가중치 형식을 사용하고, 유지관리자가 소유한 추론기로 예측을
생성한다. 학습 엔지니어에게는 학습 라벨을 제공하되 보호된 테스트 정답은 제공하지 않는다.

## 3. 모든 프로젝트에 적용할 운영 방식

새 직업마다 Agent 클래스를 추가하지 않는다. 다음 책임을 역할 설정으로 나눈다.

| 책임 | 배정할 관점/역할 설정 | 반드시 반환할 것 |
| --- | --- | --- |
| 질문과 비교 가설 결정 | Research | 반증 가능한 문장, 논문·코드 근거, 비교 대안과 제외 이유 |
| 데이터 확보·분할 | Research 기반 Data Curator 설정 | 실제 다운로드/열람 기록, 라벨 정의, 중복·누수 검사, 분할 목록 |
| CUDA·라이브러리·자원 준비 | Environment Engineer | 같은 제한 아래에서 실행한 CUDA·역전파 준비 검사 |
| 학습·개선 실험 수행 | Engineering 기반 Training Engineer 설정 | 실제 optimizer 단계, 학습 곡선, 설정, 체크포인트, 실패와 변경 이유 |
| 결과 판정 | 호스트 보호 평가기 + 독립 Auditor | 고정된 분할의 지표, 미학습/기준 모델 비교, 재현 결과 |
| 다음 실험 선택 | Research + Strategy | 예상 정보 이득, 남은 GPU 시간, 중단/계속 판단 |
| 최종 설명 검토 | Report Reader | 보고서만 읽고 행위자·데이터·모델·근거·한계를 이해할 수 있는지 |

순서는 질문 고정 → 실제 출처/데이터 읽기 → 분할·지표·예산 고정 → 작은 과적합 검사
→ 기준 모델 학습 → 측정 → 한 요인씩 바꾼 실험 → 독립 재현 → 최종 보고다.
큰 차이가 나는 결과는 즉시 사실로 채택하지 않고 분할 누수·평가 코드·설정부터 확인한다.

학습을 했다고 인정하려면 훈련 전후 파라미터 차이, 유한한 손실/기울기, 실제 optimizer
단계, 저장 가중치를 새 프로세스에서 읽어 얻은 예측을 함께 확인한다. 미학습 모델보다
낮은 손실만으로 일반화가 입증되지는 않는다. 사전학습 모델을 그대로 호출한 실험은
추론 실험으로 기록한다. 최종 성능 주장에는 기준 모델과 최종 후보 각각 3개 seed를
사용하며, 탐색 단계의 1개 seed 결과와 섞지 않는다.

모든 프로젝트는 `data-card.md`, 분할 목록, `hypotheses.md`, `baseline-config.json`,
`experiment-ledger.jsonl`, 학습 곡선, 모델 참조, 보호된 평가 영수증, `report.md`를 남긴다.
테스트셋은 최종 후보 선택 후에만 채점한다. 개선 여부에 따라 테스트셋을 다시 나누지 않는다.

현재 연구 템플릿 R4/R5에는 외부 관찰/확인 게이트가 있다. 학습 전용 워크플로를 만들 때
자동 평가와 독립 재현의 신뢰된 영수증으로 해당 단계를 정의해야 한다. 모델이 외부
사람의 확인을 만들어 내거나 기존 게이트를 임의로 통과시키는 방식은 사용하지 않는다.

## 4. 쉬움 — 학습이 실제로 이루어지는지와 기본 실험 규율

### E1. 의류 이미지 분류: MLP보다 CNN이 일반화하는가

* **데이터:** [Fashion-MNIST 공식 저장소](https://github.com/zalandoresearch/fashion-mnist).
  공식 train에서 검증셋을 분리하고 공식 test는 최종 평가로 남긴다.
* **학습 모델/가설:** 작은 MLP와 3층 CNN을 처음부터 학습한다. 비슷한 파라미터·
  업데이트 예산에서 공간 구조를 사용하는 CNN이 오류를 줄이는지 확인한다.
* **실험:** 미학습 모델 → MLP → CNN. CNN의 dropout 사용 여부 한 가지만 추가 비교한다.
* **지표/판정:** 정확도, 클래스별 재현율, 오류 예시, 학습/검증 손실, seed 변동.
  학습 재현 완료와 기준 대비 품질 개선을 따로 판정한다.
* **예산 제안:** GPU 누적 1시간, 탐색 최대 3설정. 10분 준비 실행으로 실제 소요를 확인한다.
* **시스템에서 볼 것:** 다운로드에서 새 프로세스의 가중치 로딩까지 이어지는지,
  학습하지 않은 모델을 학습 결과로 보고하지 않는지. 작은 모델의 GPU 사용률은 낮아도 정상이다.

### E2. 작은 이미지 분류: 데이터 증강이 깨끗한 이미지와 손상 이미지에 미치는 영향

* **데이터:** [CIFAR-10 공식 배포](https://www.cs.toronto.edu/~kriz/cifar.html).
  증강은 train에만 적용한다. 손상 평가용 잡음·밝기 조건도 학습 전에 고정한다.
* **학습 모델/가설:** CIFAR 입력에 맞춘 ResNet-18을 처음부터 학습한다. crop/flip이
  일반화에 미치는 영향과 강한 증강으로 깨끗한 이미지 성능이 나빠지는 경우를 구분한다.
* **실험:** 증강 없음 → crop/flip → 한 가지 추가 증강. optimizer·스케줄·step 수는 고정한다.
* **지표/판정:** clean 정확도, 고정 손상 조건의 정확도, 최악 조건, 샘플/초와 VRAM 최고점.
  가장 좋은 조건 하나만 골라 전체에 강건하다고 쓰지 않는다.
* **예산 제안:** GPU 누적 3시간, 탐색 3설정. 전체 수렴을 못 하면 제한된 epoch 실험으로 명시한다.
* **시스템에서 볼 것:** 성능이 나빠졌을 때 설치 문제 대신 과도한 증강이라는 가설을
  세우고, 실제 대조 실험으로 구분하는지. 세 프로젝트 중 첫 GPU 처리량 평가에 적합하다.

### E3. 스마트폰 센서 활동 분류: 사람을 바꾸어도 인식하는가

* **데이터:** [UCI HAR 공식 데이터](https://archive.ics.uci.edu/dataset/240/humanactivityrecognitionusingsmartphones).
  같은 사람의 인접 구간이 train/validation에 섞이지 않도록 subject 단위로 나눈다.
* **학습 모델/가설:** 원시 관성 시계열의 작은 1D-CNN과 고정 특징의 MLP를 각각 학습한다.
  원시 신호 모델이 새 사람에게도 나은지 확인한다. 입력 정보 차이는 결과 해석에 명시한다.
* **실험:** 정상 신호 학습 → 작은 시간 이동/잡음 증강 → 사람별 오류 분석.
* **지표/판정:** macro-F1, 활동별/사람별 오류, seed 분산. 랜덤 window 분할은
  누수의 영향을 설명하는 보조 실험으로만 사용하고 주 평가로 쓰지 않는다.
* **예산 제안:** GPU 누적 1시간, 데이터·특징 정의 확인에 별도 작업 시간을 둔다.
* **시스템에서 볼 것:** 높은 숫자를 얻기 쉬운 분할을 거부하고 올바른 실험을 유지하는지.
  GPU를 최대로 점유하는 프로젝트로는 적합하지 않다.

## 5. 중간 — 데이터 처리·논문 구현·자원 조정을 함께 확인

### M1. 소음에 강한 음성 명령 인식

* **데이터:** [Speech Commands v0.02](https://www.tensorflow.org/datasets/catalog/speech_commands).
  10개 명령+unknown+silence의 구성, 화자 분할, 배경 소음 출처를 먼저 고정한다.
* **학습 모델/가설:** log-mel 입력의 작은 CNN과 depthwise-separable CNN을 학습한다.
  배경 잡음 증강이 새 화자·고정 SNR 조건에서 오류를 줄이는지 시험한다.
* **실험:** 기본 CNN → 작은 모델 → 잡음 증강. 시간축 가리기 추가는 별도 요인으로 기록한다.
* **지표/판정:** clean/noisy macro-F1, SNR별 재현율, unknown 오탐, 지연 시간.
  전처리 시간과 GPU 연산 시간을 분리한다.
* **예산 제안:** GPU 누적 6시간, 탐색 4설정. 다운로드와 특징 캐시가 GPU보다 병목일 수 있다.
* **시스템에서 볼 것:** 음성 길이·샘플링·분할을 확인하고, 데이터 로딩 병목을 모델
  구조 변경과 혼동하지 않는지. 검색/읽기와 실제 구현의 연결을 보기 좋은 첫 중간 과제다.

### M2. 반려동물 영역 분할: 사전학습과 손실 함수의 효과

* **데이터:** [Oxford-IIIT Pet 공식 배포](https://www.robots.ox.ac.uk/~vgg/data/pets/).
  이미지와 trimap 마스크를 함께 확인하고 경계 픽셀을 어떤 클래스로 다룰지 고정한다.
* **학습 모델/가설:** ResNet-18 encoder의 U-Net. 무작위 초기화와 공개 사전학습
  초기화를 비교하고, 작은 데이터에서 전이학습이 유리한지 시험한다.
* **실험:** scratch → pretrained → 같은 초기화에서 CE와 CE+Dice 비교.
  mask resize는 nearest-neighbor로 하며 입력/마스크 증강 좌표가 같은지 검사한다.
* **지표/판정:** mIoU, Dice, 경계 오류, 같은 이미지의 예측 마스크. 시각적으로 예쁜
  몇 장과 전체 지표를 분리하고 실패한 마스크도 보고한다.
* **예산 제안:** 256×256 입력으로 시작, GPU 누적 8시간. 배치와 AMP를 준비 실행에서 결정한다.
* **시스템에서 볼 것:** 라벨 전처리 오류를 실제 샘플에서 찾아 수정하는지,
  체크포인트가 16MB 경계를 넘었을 때 새 모델 저장 계약으로 전달되는지.

### M3. 악보의 작은 기호 검출: 타일링이 notehead 검출을 개선하는가

* **데이터:** [DeepScoresV2 dense](https://zenodo.org/records/4012193).
  전체판 대신 1,714개 이미지의 dense 배포를 선택한다. 공식 배포 기준 dense 압축본은
  약 742MB이며 전체판은 약 80.9GB이다. 이 머신의 현재 여유 공간에서는 전체판을 받지 않는다.
* **학습 모델/가설:** 유지되는 프레임워크의 Faster R-CNN+FPN 검출기를 미세조정한다.
  축소한 전체 페이지보다 겹치는 타일이 작은 기호 재현율을 높이는지 확인한다.
* **실험:** 페이지 축소 → 타일 학습/추론 → 한 가지 anchor/해상도 조정.
  주 클래스 10개의 선택 규칙과 포함/제외 대상을 데이터 확인 후 test 열람 전에 고정한다.
* **지표/판정:** 기호별 AP50/재현율, 작은 기호 성능, 페이지당 시간. 타일은 원본 페이지를
  먼저 분리한 뒤 생성하고, 경계 중복과 누락은 페이지 좌표로 합쳐 채점한다.
* **예산 제안:** GPU 누적 12시간, 탐색 4설정, 512×512 타일에서 시작한다.
* **시스템에서 볼 것:** 공식 논문의 오래된 코드/의존성과 현대 구현을 구분하고,
  포팅했다면 원 논문 재현이라고 과장하지 않는지. 기호 검출 성공은 악보 전체 복원이 아니다.

## 6. 어려움 — 가설 수정·표현·평가·전이를 묶어 평가

### H1. 한 줄 악보 이미지를 음표 시퀀스로 바꾸는 모델

* **데이터:** [PrIMuS / Camera-PrIMuS 공식 배포](https://grfia.dlsi.ua.es/primus/).
  원본 incipit 단위로 나눈다. 같은 악구의 다른 폰트·왜곡본은 같은 분할에 둔다.
* **학습 모델/가설:** CNN+BiLSTM+CTC로 semantic token을 출력한다. 렌더링 악보에서
  학습한 모델에 카메라 왜곡 증강을 주면 왜곡 입력의 시퀀스 오류가 줄어드는지 시험한다.
* **실험:** 깨끗한 이미지 학습 → 왜곡 증강 → 실제 Camera 조건 평가. 작은 Transformer
  비교는 예산이 남을 때 별도 구조 가설로 수행하며 동시에 여러 요인을 바꾸지 않는다.
* **지표/판정:** symbol error rate, 악구 완전일치율, 음높이/길이 오류, 파싱 성공률.
  token→음악 표현 변환을 별도 단위 시험으로 검증한다.
* **예산 제안:** GPU 누적 18시간. 처음에는 train 최대 20,000 악구의 고정 부분집합을 쓰고
  10분 probe에서 메모리와 처리량을 측정한다. 부족하면 범위를 낮추고 전체 데이터 결과로 쓰지 않는다.
* **시스템에서 볼 것:** CTC 정렬 실패, 잘못된 vocabulary, 긴 시퀀스 오류 중 어느 문제인지
  분리하고 실제 측정으로 가설을 바꾸는지. 단선율 한 줄 과제이며 다성부 전체 페이지는 포함하지 않는다.

### H2. 한국어 음성 전사 모델의 적은 데이터 미세조정

* **데이터:** [Google FLEURS](https://huggingface.co/datasets/google/fleurs)의 `ko_kr`만 선택한다.
  제공 분할을 보존하고 같은 문장 중복 여부를 추가 확인한다. 전체 언어를 내려받지 않는다.
* **학습 모델/가설:** [공개 Whisper-small](https://github.com/openai/whisper) 기준 추론과 LoRA 미세조정을 비교한다.
  소량 한국어 학습이 해당 분포를 개선하는지, 조용한 음성 성능을 잃는지도 확인한다.
* **실험:** 사전학습 추론 → LoRA → 학습률/정규화 한 요인 조정. 언어·전사 작업 설정,
  디코딩 옵션과 문자 정규화는 모든 비교에서 동일하게 유지한다.
* **지표/판정:** 한국어 CER을 주 지표로 하고 WER도 명시된 정규화 아래 보고한다.
  실시간 계수, VRAM, 화자/잡음별 오류와 미세조정 전후 동일 문장의 출력을 비교한다.
* **예산 제안:** GPU 누적 18시간, batch 1~4와 accumulation으로 시작하되 실제 측정 후 고정한다.
  16GB에 맞지 않으면 Whisper-tiny로 범위를 바꾸고 small 실험과 혼합하지 않는다.
* **시스템에서 볼 것:** 원 모델 추론을 학습이라고 쓰지 않는지, adapter 가중치가 바뀌고
  새 프로세스에 로드되는지, 사전학습 데이터 중복 가능성과 도메인 한계를 명시하는지.

### H3. 첨부 악보 32개를 편집·전조 가능한 표현으로 복원하는 전체 연구

* **데이터:** 사용자의 32개 악보를 고정 개발 평가로 사용한다. 학습은 별도 허가된
  DeepScores/PrIMuS 및 필요한 합성 데이터에서 수행한다. 현재 보호된 `.krn` 정답을
  학습 에이전트에게 넘기지 않는다. 별도의 곡/페이지를 최종 일반화 평가로 확보한다.
* **학습 모델/가설:** 악보 영역·기호 검출기와 음표/리듬 시퀀스 모델을 학습/미세조정한다.
  구조 기반 규칙과 비교하여 어떤 실패 유형에서 학습이 도움이 되는지 확인한다.
  학습이 필요 없는 파싱·MusicXML 작성·전조는 결정적 코드로 유지할 수 있다.
* **실험:** 공개 OMR 프로그램을 실제 설치·실행·채점 → 실패 유형 표 → 한 실패 유형에 대한
  학습 개입 → 전체 32개 재평가 → 실제 음악가 확인. 공개 후보를 생략하면 실행하지 않은
  이유와 대체 비교를 기록한다. 기존 실행 결과를 새 설치 비교 결과로 쓰지 않는다.
* **지표/판정:** 음높이·길이·쉼표·화음·화음 시점·성부 오류, 모든 입력의 처리율,
  편집 가능성, C→D 등 전조의 간격/리듬 보존을 따로 검사한다. 누락 파일도 전체 분모에 남긴다.
* **정답 확인:** 이미지와 `.krn`이 정말 대응하는지부터 음악가가 확인한다. 모호한
  참조는 판정 유보로 남기고 원본을 고쳐 점수를 맞추지 않는다. 보정 gold가 필요하면
  독립 검토와 새 버전으로 관리한다.
* **예산 제안:** 첫 사이클 GPU 누적 24시간, 도구·데이터 준비 2~3일의 작업 범위.
  이것은 완성 기한 약속이 아니다. 32개 100%는 원래의 목표로 남기되 도달하지 못하면
  실패·한계로 보고한다. 32개에 적응한 결과를 새 악보 일반화 성능으로 쓰지 않는다.
* **시스템에서 볼 것:** 논문·도구·학습을 실제 실패 사례에 연결하고, 필요한 개발을
  구체적 입력·중간 출력·해결 시험과 함께 배정하는지. 첫 성능 시험으로는 너무 복잡하다.

## 7. 결과로 에이전트 시스템을 어떻게 평가할까

각 과제의 모델 점수와 **그 점수가 만들어진 업무의 신뢰성**을 함께 평가한다.
다음은 점수 하나로 합치기 전에 통과해야 하는 확인 항목이다.

| 확인 항목 | 관찰할 구체적 증거 |
| --- | --- |
| 데이터를 실제 확보했는가 | 읽을 수 있는 원본, 라벨 예제, 수량, 버전, 실패한 접근과 대체 경로 |
| 학습을 실제 수행했는가 | optimizer 단계·기울기·전후 파라미터 차이·새 프로세스의 체크포인트 추론 |
| 비교가 공정한가 | 동일 분할·동일 채점·고정 탐색 예산, 변경한 요인, seed별 원 결과 |
| 실패를 해결했는가 | 오류/이미지/중간 출력이 연결된 업무, 책임자, 해결 시험, 수정 후 결과 |
| 자원을 효과적으로 썼는가 | 학습 구간 샘플/초·데이터 대기·VRAM·재시작 손실·품질/GPU 시간 |
| 보고가 근거와 맞는가 | 주장→읽기/실행/평가 기록의 연결, 보고서만 받은 검토자의 이해 여부 |

비교 대상은 같은 모델/데이터/도구 권한을 가진 **단일 에이전트**와 현재 팀이다.
총 모델 토큰·호출, 탐색 설정 수, GPU 시간, 데이터 접근 범위를 맞춘다. 팀에 더 많은
예산을 주고 구조 덕분에 좋아졌다고 해석하지 않는다. 쉬운 과제는 독립 실행 3회,
어려운 과제는 먼저 1회 운영 문제를 찾고 비교 실행 수를 늘린다. 이미 정답을 본 실행은
동일 조건의 새 평가로 세지 않는다.

논문 재현이 실패해도 근거 있는 실패를 도출한 연구는 유용할 수 있다. 다만
`study_completed`와 `quality_target_met`을 별도로 기록한다. 성능 미달을 문서가
완료되었다는 이유로 성공으로 바꾸지 않는다. 사용률 100%, 보고서 페이지 수,
역할 호출 수는 연구 품질의 대리 지표로 쓰지 않는다.

## 8. 권장 착수 순서

1. GPU 프로필·데이터/모델 저장 계약·보호된 모델 평가·학습 작업 관리를 먼저 준비한다.
2. **E1 → E2:** 역전파/저장/재개/평가가 실제로 되는지와 GPU 처리량을 각각 확인한다.
3. **M1:** 음성 데이터 전처리, 논문/오픈소스 확인, 실패 원인 분리까지 검사한다.
4. **M3 → H1:** 사용자의 악보 목표에 필요한 기호 검출과 시퀀스 인식을 따로 검증한다.
5. H3는 앞 단계에서 얻은 검증 가능한 모듈과 자료를 통합하는 최종 과제로 수행한다.

가장 먼저 해 볼 프로젝트는 E1, 연구 시스템의 의미 있는 첫 평가는 M1,
사용자 목표와 직접 연결되는 다음 단계는 M3를 권한다. 프로젝트 아홉 개를 동시에
돌리는 계획은 아니다. 한 GPU에서는 한 학습 작업을 기본으로 하고 자료 확인·보고
같은 CPU 작업만 병행 가능한 구조를 이후 설계한다.

참고: [NVIDIA WSL 지원과 제한](https://docs.nvidia.com/cuda/wsl-user-guide/),
[Docker GPU 전달](https://docs.docker.com/engine/containers/gpu/).
위 예산과 목표는 설계 제안이며 해당 장비에서 측정한 학습 시간·성능 예측값이 아니다.
