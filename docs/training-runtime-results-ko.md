# 학습 도구·런타임·디버깅 구현 및 실측 기록

작성일: 2026-10-30. 대상: ResearchSquad의 `feat/training-runtime-traces` 변경.

이번 버전은 에이전트가 Python 학습 코드를 작성한 뒤 승인된 GPU 환경에서
백그라운드 작업을 시작하고, 기다렸다가 체크포인트와 모델을 등록하고,
별도 평가기에 채점을 요청할 수 있게 한다. 모든 역할은 기존 공통 `Agent`를
재사용한다. 도구 권한은 역할 JSON, 관점과 작업 지침은 프롬프트,
실행 상태와 강제 규칙은 Team과 런타임이 맡는다.

Fashion-MNIST를 실제 GPU에서 학습시켜 저장·재개·독립 채점을 검증했다.
이 검증에서 작업 선택과 리뷰 응답은 고정된 시나리오다. 에이전트가 스스로
논문을 읽고 모델을 고른 연구 실험과는 구분해야 한다. 별도의 실제 Codex
호출은 프롬프트·도구·결과 추적을 확인하는 작은 작업에 사용했다.

## 작업 순서와 책임

사용자가 제안한 런타임/도구 → 디버깅 → Fashion-MNIST 순서에 두 가지를
보완했다. 먼저 계약과 성공 조건을 정의했고, 디버깅은 런타임과 함께 구현했다.
학습이 실패한 뒤 로그를 추가하면 최초 실패의 원인을 잃기 때문이다.

1. 실행 프로필, 작업 ID, 상태, 데이터·모델 참조, 평가 어댑터의 계약을 정했다.
2. 도구와 런타임을 구현하면서 모델 호출·도구 호출·호스트 이벤트 추적을 붙였다.
3. 실제 CPU 컨테이너로 호스트 재시작, 시간 제한, 취소, 큰 파일 저장을 확인했다.
4. CUDA 컨테이너에서 import뿐 아니라 실제 역전파가 되는지 확인했다.
5. Fashion-MNIST의 학습, 체크포인트 재개, 별도 평가와 기존 프로젝트 게이트를 연결했다.
6. 전체 회귀와 기존 managed workflow를 다시 확인하고 결과와 한계를 기록했다.

이번 구현 자체는 이 대화의 담당자가 수행했다. 구현 작업을 여러 개발 에이전트에게
나누어 진행했다는 주장은 하지 않는다. 아래의 Engineering·Auditor·Report Reader는
완성된 시스템의 통합 검증에서 사용한 역할이다.

## 무엇을 도구에, 무엇을 런타임에 넣었는가

도구는 에이전트가 의도를 표현하는 인터페이스다. 예를 들어 `start_job`은
프로필과 소스 목록을 제출하고, `await_job`은 기다리겠다는 요청을 제출한다.
프롬프트가 “기다려라”라고 말하는 것만으로 프로세스의 생명주기가 관리되지는 않는다.

런타임은 모델 호출이 끝나거나 담당 역할이 바뀌어도 유지되어야 하는 사실과
강제 규칙을 맡는다. 컨테이너가 실제로 실행 중인지, 누가 만든 작업인지,
허용된 이미지와 자원 한도인지, 같은 요청을 재실행하는지, 어떤 체크포인트에서
이어졌는지를 모델의 자기 보고 대신 호스트가 관리한다. Team만 상태와 이벤트를
저장하며, 별도의 경쟁하는 상태 DB를 만들지 않았다.

새 기능을 배치하는 기준도 같다. 특정 연구의 가설·모델 선택은 역할과 과제의
책임이다. 여러 과제에 공통이며 재시작·권한·자원·근거의 일관성을 강제해야 하는
기능은 런타임에 둔다. 패키지나 외부 시스템에 접근하는 행위는 도구로 노출한다.
Fashion-MNIST 전용 CNN이나 정확도 기준을 일반 런타임에 넣지 않았다.

## 구현된 인터페이스

| 도구 | 실제 동작과 산출물 |
| --- | --- |
| `training_catalog` | 승인된 프로필, 공개 등록 데이터, 모델 참조를 확인한다. |
| `register_dataset` | 작업 공간의 명시된 파일을 스트리밍 등록한다. 호스트 경로나 보호 평가 자료를 지정할 수 없다. |
| `start_job` | 소스를 고정하고 격리된 컨테이너를 시작해 작업 ID를 돌려준다. |
| `job_status` / `read_job_output` | Docker 상태, 종료 정보, 제한된 로그·파일 목록과 텍스트 출력을 읽는다. 자체 보고 정확도는 독립 측정으로 취급하지 않는다. |
| `await_job` | 같은 업무 ID를 유지한 채 대기한다. 호스트가 종료를 관찰한 뒤 담당자를 계속 실행한다. |
| `cancel_job` | 소유한 작업을 중단한다. 이미 저장된 파일은 보존하며 새 체크포인트 생성을 보장하지는 않는다. |
| `register_model` | 종료한 작업의 모델 또는 체크포인트를 큰 파일 저장소에 고정한다. |
| `resume_job` | 같은 소스·프로필·데이터와 등록된 체크포인트로 새 시도를 시작한다. |
| `evaluate_model` | 관리자가 등록한 버전 있는 평가 어댑터에 고정 모델을 제출한다. |
| `record_decision` | 짧은 공개 판단과 명시적으로 제안한 후보·보류 이유를 기록한다. |

일반 텍스트 산출물에 모델을 억지로 넣지 않는다. 모델과 데이터는 스트리밍
파일 저장소에 두고, 역할 사이에서는 작은 참조 ID를 전달한다. 같은 내용의
참조가 훼손되지 않았는지는 사용 전에 검사한다. 보고서를 읽는 사람에게
해시 문자열을 성능 지표처럼 제시하지는 않는다.

승인 프로필은 이미지의 고정 식별자, GPU 사용 여부, 시스템 RAM, CPU, 작업별
시간·출력 크기와 사용 가능한 역할을 정한다. 기본 역할에는 새 권한을 붙이지
않았고, `agents/training/`을 명시적으로 선택한다. 학습 코드는 네트워크·호스트
환경 변수·프로젝트 전체·Docker 소켓을 받지 않는다. 감독 프로세스는 시간과
출력을 감시하고 학습 자식 프로세스의 권한을 낮춘다.

## Fashion-MNIST에서 역할과 데이터가 이동한 경로

| 단계 | 책임자와 입력 | 실행 및 다음 담당자에게 넘긴 것 |
| --- | --- | --- |
| 준비 | 호스트, 공식 배포 파일 | 공식 train 이미지·레이블만 공개 데이터 저장소에 등록했다. 공식 test 이미지·레이블은 학습 작업에 전달하지 않았다. |
| 실험 | Engineering, 승인 GPU 프로필과 train 참조 | 고정 CNN 소스를 작성하고 1 epoch 학습을 시작했다. 작업 ID와 실행 근거가 남았다. |
| 대기 | 런타임, 작업 ID | 모델을 반복 호출하지 않고 Docker 종료를 관찰했다. 다른 준비된 업무를 실행할 수 있다. |
| 저장·재개 | Engineering, 종료 작업과 체크포인트 참조 | 모델·Adam 상태·epoch/step·CPU/CUDA RNG를 복원해 2번째 epoch를 실행했다. |
| 비교 | Engineering, 같은 소스·데이터·seed | 처음부터 2 epoch 연속 학습한 별도 모델도 만들었다. |
| 채점 | 관리자가 고정한 평가 어댑터, 저장된 safetensors와 비공개 test 10,000개 | 별도 CPU 컨테이너에서 관리자의 CNN 구조로 로드하고 정확도·손실을 계산했다. 학습 코드의 평가 함수를 실행하지 않았다. |
| 검토 | Auditor 및 Report Reader | 별도 문맥에서 전달된 산출물을 검토했다. Report Reader는 보고서만 받는다. 이 검증의 검토 응답은 시나리오로 고정했다. |
| 단계 판단 | Coordinator와 호스트 게이트 | 필수 검토와 해당 모델에 연결된 보호 측정이 모두 있어야 단계를 승인했다. 보고서 DONE만으로 완료하지 않았다. |

통합 검증의 호출 선택 26회는 실제 `Agent`·도구·managed workflow를 통과하는
고정 응답이다. 학습·데이터 저장·Docker 실행·모델 채점은 실제 연산이다.
이 둘을 합쳐 “LLM이 26번 판단해 새로운 모델을 발견했다”고 해석하면 안 된다.

## 측정 조건과 결과

Windows 호스트의 Ubuntu 24.04 WSL과 Docker를 사용했다. GPU는 RTX 3080
Laptop GPU 16GB이고, 학습 환경은 PyTorch 2.9.1+cu128 / CUDA 12.8이다.
환경 빌드 시 import와 역전파를 확인하고 실제 설치 패키지 목록을 기록했다.
실행 프로필은 검토한 빌드 이미지의 고정 ID를 사용한다.

모델은 Conv 32 → Conv 64 → FC 1024 → 10 클래스의 고정 CNN이다.
seed는 1337, Adam 학습률은 0.001, batch size는 512다. 공식 train 60,000개 중
마지막 5,000개를 validation으로 분리하고 55,000개로 학습했다. 공식 test
10,000개는 별도 평가기에서만 사용했다. 2 epoch라는 짧은 설정은 시스템의
학습·복구 경로를 확인하기 위한 것이며 정확도 최적화 실험이 아니다.

| 확인 대상 | 결과와 의미 |
| --- | --- |
| 실제 학습 | 손실이 1 epoch 0.62755에서 2 epoch 0.37029로 감소했다. gradient는 유한했고 첫 convolution 파라미터가 바뀌었다. 단순히 CUDA 장치를 조회한 검증이 아니다. |
| Validation | 84.44% → 87.88%. 보호 test를 사용한 모델 선택은 하지 않았다. |
| 독립 test | 학습 모델 86.97%, 같은 seed의 미학습 모델 14.48%. 사전에 고정한 최소 80% 및 미학습 대비 개선 조건을 통과했다. |
| 체크포인트 | 38,913,781 bytes. 기존 텍스트 산출물 상한을 넘는 파일을 저장·등록·재개 입력으로 전달했다. |
| 재개 일치 | 1 epoch 뒤 저장하고 재개한 모델과 2 epoch 연속 모델의 최종 가중치 최대 차이가 0이었다. 동일 환경에서의 epoch 경계 재개 일치다. |
| 재실행 방지 | 완료된 Team을 다시 실행해도 시나리오 호출이 추가되지 않았다. CPU 검증에서는 Team을 실제로 닫고 다시 열어 분리된 작업을 회수했다. |
| 시간 제한·취소 | 실제 CPU 컨테이너가 제한 시간에 종료 코드 124로 끝났고, 별도 취소 작업은 CANCELLED로 기록됐다. |

두 고정 모델에 같은 test 평가를 요청한 이유는 재개와 연속 실행의 결과를
확인하기 위해서다. test 결과를 보고 하이퍼파라미터를 고르지는 않았다.
보고된 학습 구간 시간과 최대 할당 VRAM은 데이터 준비·컨테이너 시작을 포함한
전체 서비스 성능이나 GPU 사용률을 의미하지 않는다. 작은 CNN은 약 0.5GB의
할당 VRAM만 사용했으므로 하드웨어를 100% 활용했다고 결론 내릴 수 없다.

## 디버깅 화면에서 무엇을 볼 수 있는가

실행 폴더의 `traces/`에는 모델·도구·역할 실행·호스트 이벤트의 연결된 기록이
저장된다. `python -m goalagent.tracing --run-dir ... --output trace.html`로
필터 가능한 단일 로컬 HTML을 만든다. 다른 에이전트를 동기 호출하면 그
호출 아래에 자식 실행이 연결된다. managed workflow의 배정은 호스트가
수행한 이벤트로 표시하며 LLM이 직접 호출한 것처럼 꾸미지 않는다.

모델 호출을 펼치면 적용된 system prompt, 논리적 messages/context, 실제로
provider에 보낸 결합 프롬프트, 사용 가능한 도구, 선택한 액션과 공개 `why`,
모델·사용량 정보 및 오류를 확인할 수 있다. 현재 CLI provider는 하나의
결합 프롬프트를 보내므로 지속적인 채팅 메시지 배열과 혼동하지 않도록 표시한다.
도구 호출에는 인자·결과·에러가 연결된다. 후보는 `record_decision`에 명시적으로
쓴 경우에만 존재한다. 도구 목록만 보고 모델이 모든 도구를 고려했다고 추정하지 않는다.

모델의 비공개 내부 사고는 수집하지 않는다. 디버깅에 필요한 것은 전달된 정보,
표명한 판단, 선택한 행동과 실제 결과의 연결이다. 오류를 찾을 때도 이 연결로
“데이터를 받았는가 → 실행했는가 → 무슨 결과인가 → 무엇을 근거로 승인했는가”를
확인한다. 원인을 기록에서 확정할 수 없으면 모르는 것으로 남긴다.

실제 Codex `gpt-6-astra`를 3회 호출한 별도 작업에서는 입력 읽기 → 파일 쓰기 →
보고서 제출의 프롬프트와 도구 결과가 남는 것을 확인했다. 이 작은 작업은
학습 실험이 아니며 보호 평가기도 없어서 `goal_met`은 false다. 반대로 Fashion
trace의 model span은 고정 응답 제공자가 만든 것으로 표시한다.

알려진 토큰 패턴과 credential 필드는 새 trace에서 가린다. 완전한 비밀 탐지기는
아니며 기존 provider 원본 로그까지 정리하는 기능은 아니다. 현재는 로컬 파일과
HTML export이며 호스팅·다중 사용자 관제·대규모 검색 서비스는 구현하지 않았다.

## 실패가 실제로 막은 업무와 수정

| 실패 | 막힌 업무와 관찰 | 수정과 이후 확인 |
| --- | --- | --- |
| Docker log 옵션 충돌 | 최초 CPU 작업을 시작할 때 local driver의 압축 옵션과 단일 파일 설정이 충돌해 컨테이너가 뜨지 않았다. 학습 가설의 실패가 아니다. | 압축을 끄고 Docker 오류 stderr를 보존했다. 실제 분리 실행이 성공했다. |
| WSL 상대 경로 재개 | Docker 실행 뒤 상대 폴더로 Team을 다시 열 때 DrvFS의 현재 디렉터리 오류가 발생해 회수 검증이 중단됐다. | 검증 시작 시 실행 폴더를 절대 경로로 고정했다. 닫기·재열기 검증이 성공했다. |
| 감독자의 프로세스 종료 권한 | 낮은 UID의 자식 학습 프로세스를 root 감독자가 제한 시간에 죽이는 단계에서 권한 오류가 났다. | 감독자에만 KILL capability를 주고 자식 권한은 유지하지 않았다. 실제 timeout 종료 코드 124를 확인했다. |
| CUDA 이미지 패키지 누락 | 첫 Fashion 작업에서 `safetensors.torch`가 요구하는 `packaging`을 찾지 못해 모델 저장 이전에 실패했다. | 패키지를 고정 추가하고 이미지 빌드에 import·gradient smoke check를 넣었다. 고정 이미지로 학습·저장·평가를 다시 통과했다. |
| 고정 검증 시나리오의 후속 진행 | 위 실패 뒤에도 시나리오가 성공 경로의 다음 번호를 선택해 불필요한 호출을 소모했다. | 실제 작업이 실패하면 FAILED 보고로 종료하게 고쳤다. 최초 실패 기록은 남겼다. 일반 역할이 자동으로 환경을 고쳤다는 증거로 삼지 않는다. |
| 실행 중 출력의 경로 경쟁 | 새 도구가 살아 있는 학습 작업의 파일을 읽으므로 과거의 '종료한 컨테이너' 가정이 맞지 않았다. 부모 디렉터리 교체로 다른 파일을 읽을 가능성이 생겼다. | 읽는 동안 각 부모 경로와 최종 파일을 descriptor로 고정했다. 디렉터리 교체 회귀와 제한된 파일 목록 검증을 추가했다. |
| 시작과 완료 근거의 혼동 | start 결과나 RUNNING 상태 질의를 인용해 '학습 완료'로 보고할 수 있는 틈이 있었다. | `job_started`와 `job_completed`를 나누고 완료는 SUCCEEDED 관찰 근거만 허용했다. 거짓 완료 주장 거부 테스트를 추가했다. |

이 수정들은 정확도를 올리기 위해 정답이나 평가 기준을 바꾼 것이 아니다.
실행·관찰·복구·보고 사이에서 무엇이 실제로 일어났는지 보존하는 작업이었다.

## 유지할 구조와 부족한 부분

공통 Agent, 역할별 JSON/프롬프트, Team 단일 상태 기록, 독립 평가와 별도 보고서
검토는 유지할 구조다. 새 학습 경로도 같은 업무 ID와 근거·게이트 체계 안에서
동작하므로 학습 전용 평행 시스템을 만들 필요가 없었다.

부족한 부분은 구체적으로 다음과 같다.

- **자율 연구는 아직 평가하지 않았다.** 이번에는 CNN·데이터 분리·실험 순서가 고정됐다. 다음 검증은 실제 모델이 공개 후보나 논문을 읽고, 제한된 예산으로 가설을 선택하고, validation 결과로 수정하도록 해야 한다. 사전 정의된 test는 최종 비교에만 쓴다.
- **재개 지원은 학습 코드의 책임이 남아 있다.** 이 예제는 Adam과 RNG를 복원했지만 모든 framework·scheduler·분산 sampler·중간 batch 복구를 자동 처리하지 않는다. 새 학습 코드는 자체 일치 검증이 필요하다.
- **하드웨어 최대 활용을 검증하지 않았다.** GPU 시작을 ResearchSquad 작업 사이에서 직렬화하지만 다른 앱을 막지는 않는다. VRAM hard quota, 사용률 시계열, 다중 GPU·원격 학습과 총 GPU 시간 회계가 없다. 이를 측정한 뒤 batch/입력 병목을 조정해야 한다.
- **저장소 운영이 부족하다.** 큰 파일은 실행별 저장소다. 실행 간 중복 제거, 정리 정책, 보존 UI, 원격 전송·백업이 없다. 출력 크기 감시는 주기적 검사여서 순간적인 디스크 초과를 완전히 차단하지 못한다.
- **모델별 평가 어댑터가 필요하다.** 임의의 agent Python을 평가 호스트에서 실행하지 않는다. 새로운 모델 구조·과제에는 관리자가 검토한 loader와 과학적 기준을 등록해야 한다. 일반 CLI가 임의 어댑터를 자동 로드하지 않는다.
- **불확실한 외부 실행은 자동 반복하지 않는다.** 컨테이너 시작 응답을 잃거나 컨테이너가 사라지면 START_UNCERTAIN/LOST로 남긴다. 실제 상태를 확인하고 다음 조치를 고르는 운영자 절차가 필요하다.
- **trace 운영은 초기 버전이다.** 실시간 대시보드, 대규모 저장·집계·보존, 비용 비교와 완전한 민감정보 제거가 없다. 이번 기능은 한 실행에서 업무 전달과 행동의 연결을 조사하는 로컬 디버거다.

`sessions/01a183b6-agent-system/reports/training-runtime-20261030/`에 분리한다.
