What failed, and why

small-staff — confirmed execution failure

Audiveris rejected 31/32 original crops; logs report staff spacing of roughly 6–10 pixels as too low. Enlarging and padding allowed all 32 to emit output.

Why: Its scale-estimation assumptions reject small staff geometry before recognition. This is an input compatibility failure, not evidence that the song is unreadable.

Discriminating test: Separate enlargement from padding on fixed inputs if continuing with Audiveris.

engine.log · results.json

text-recovery — confirmed null intervention

None of seven enlarged Audiveris outputs contained a whole OCR word matching the chord grammar. Five had no OCR words; two had garbled text. The adapter promoted zero chords.

Why: An adapter cannot recover chord text that the upstream recognizer never emitted. The earlier hypothesis failed at its prerequisite.

Discriminating test: Use a recognizer trained for lead-sheet harmony or read chord image regions directly.

vision-pitches — observed error; internal model cause unproven

In 내입술로_1 the candidate changes an F4 eighth note to G4. In 내입술의_1 it changes the second of two C4 sixteenth notes to D4.

Why: These are one-step staff-position errors in small raster images. Pattern completion or limited spatial discrimination are hypotheses, not established internal causes. The first candidate reported no uncertainty.

curve-endpoints — observed notation reconstruction error

In 내입술의_1 an E4–D4 slur becomes a D4–D4 tie; the next half note is merged with the preceding sixteenth note.

Why: The curve was assigned the wrong endpoints and meaning. A syntactically valid tie then changes playback and the normalized event count. Four edit-distance operations across the pilot arise from three local recognition mistakes, not necessarily four independent causes.

Discriminating test: Check visible curve endpoints independently; do not repair based on musical plausibility alone.

chord-timing — confirmed metric blind spot

The G/B label in 내입술의_1 is correct but placed at elapsed beat 5/2 instead of 7/2: one quarter-note beat early.

Why: The old chord metric discarded onset time. Matching all 38 labels did not establish correct chord placement.

Discriminating test: Add label-plus-onset scoring; mark null-melody chord rows unscorable rather than guess their times.

timing.py · prediction.krn

transpose-check — previously fixed evaluator bug

The checker treated octave-free chord labels as octave-specific pitches. B to C# looked like minus ten semitones.

Why: Chord roots and bass labels need pitch-class arithmetic modulo 12, while melody notes need absolute-pitch checks.

Discriminating test: Keep independent hand-calculated boundary tests and preserve old evaluator versions.

neural-domain — coverage failure confirmed; domain-shift explanation is a hypothesis

Transcoda emitted no harmony spine and sometimes repeated invented note sequences; four outputs reached the generation limit.

Why: The tested output path does not cover the required chord symbols. Its full-page synthetic-training regime differs from short church lead-sheet crops; this may contribute to repetition, but has not been isolated causally. A publisher-sample control worked.

Discriminating test: Test a lead-sheet model with chord-capable tokenization before considering more orchestration.

              Each role has one goal and restricted inputs

              RoleGoalAllowed structured inputs
              controllerChoose informative experiments within the fixed goal and budget; report unmet requirements honestly.budget, goal, observations
              transcriberRecover the visible melody and chord symbols faithfully in the specified editable format.format
              reviewerFind image-supported mistakes in a candidate transcription and propose minimal corrections; abstain on ambiguity.candidate, format
              scorerMeasure frozen predictions against fixed references using versioned deterministic metrics.metric_version, references, sealed_predictions

              Transcriber and reviewer also receive the image attachment. The scorer is trusted deterministic code, not an LLM. It must see references to calculate accuracy, but can do so only after the batch is frozen. It cannot revise predictions or send answers back into this run.

              • Explicit role goals and allowlisted model-input fields
              • Fresh tool-disabled reviewer context with only image and candidate
              • Temporary working directory outside the project
              • Every case reviewed, without revealing which cases failed
              • Whole batch sealed before the separate scorer opens labels
              • Hashes checked before scoring; no reviewer calls after sealing
              • No score-directed selection or retries inside this run

              Scope of protection: explicit model-input and tool separation. The CLI process is not inside an OS filesystem jail; tool-using workers need a separately isolated service/container with no reference mount.

              Existing solutions selected for this task

              Start from the concrete constraints: small lead-sheet crops, melody plus chord symbols, Humdrum, transposition, independent scoring, persistent goal-directed control. Follow primary project and framework sources; do not rank by multi-agent keyword popularity.

              Jazzmus / Optical Music Recognition of Jazz Lead Sheets — Recognition model

              The task is explicitly melody plus chord symbols at staff level, with **kern and **mxhm output. This is a closer task match than a full-page melody-only path.

              Read the paper HTML, official project, repository, inference source and model card. Public code and model checkpoint are available.

              Limits: Trained for jazz handwriting and synthetic fonts. Publisher warns about chord errors, implicit accidentals and different printed genres. No performance claim on the church data.

              Decision: Highest-priority open-source recognition candidate for a subsequent paired benchmark; not installed or run in this investigation.

              Primary source
              Soundslice — Existing user-facing product

              Scans images/PDFs into editable notation, recognizes chord names, transposes, and exports MusicXML. Could already address much of the church workflow.

              Read official scanner and supported-notation documentation.

              Limits: Vendor capabilities, not an independent accuracy result. Its documented pickup-bar limitation matters for our cropped inputs. Our local .krn chord dialect would need a tested MusicXML conversion.

              Decision: Useful product comparator. No account created, purchase made, or church data uploaded.

              Primary source
              ScanScore 3 — Existing user-facing product

              Official FAQ documents note/lyric/chord recognition, editing, transposition and MusicXML export.

              Read official FAQ.

              Limits: Not benchmarked on our input; product capability does not establish quality. A .krn conversion remains necessary.

              Decision: Another product comparator; not purchased or run.

              LangGraph — Agent orchestration

              Supports separate subgraph message histories through explicit input/output mapping and durable checkpoints. Fits per-agent goals and resumable work.

              Read current official subgraph and persistence docs.

              Limits: Private state schemas are not OS security boundaries and do not automatically prevent a developer from passing answers. It does not supply a music recognizer or objective.

              Decision: Good foundation when expanding the prototype. We retained the small existing runner for this controlled review experiment; no claim that a framework migration improves recognition.

              Has solvers, separate scorers, deferred scoring, logs and tool sandboxing. Reduces the amount of evaluation plumbing to maintain.

              Read official solver, scoring and sandbox docs.

              Limits: TaskState exposes target to solver code. Choosing this framework alone does not guarantee blinding. Must deliberately exclude targets from model inputs and tool environments.

              Decision: Prefer as evaluation infrastructure for larger campaigns after adapting our image provider and music metrics; not installed this turn.

              Decision: Use as an external comparison metric, while retaining explicit chord timing and musician correction time.

              What this does not establish

              • Development pilot, not held-out accuracy; labels were seen during prior development.
              • All outputs were frozen before this scorer loaded references; no answer feedback to the reviewer.
              • Same underlying model in two roles: independence of context does not ensure independence of errors.
              • Timed chords checked only where explicit rhythmic rows permit it; labels are not musician-audited.
              • Model confidence and blank uncertainty lists are not correctness certificates.
              • Blindness prevents one leakage route; it does not guarantee correct analysis.
              • All 32 supplied excerpts were already used in development; none can be rebranded as untouched test data.
              • Fresh test songs and independent musician adjudication are needed for generalization and label quality.
              • For tool-using agents, use a separate container/service with no reference mount and separate credentials; current CLI isolation is application-level, not a hostile-process security boundary.
